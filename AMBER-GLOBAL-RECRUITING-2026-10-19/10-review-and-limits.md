# The independent code reviews, what they found, and the limits that remain

Written 19 Oct 2026 (Pacific). There were three reviews, each by a Claude session that had not written the code. The first reviewed the lane; the second reviewed the fixes to it; the third reviewed the commit that prepared the live demonstration (both further down). After the recruiting lane was built and tested, the first reviewing session that had not written the code was asked to attack it: to read it as a hostile page, a careless owner and a scripted client would, and to run what it claimed. It reviewed commit `edaa2ef4`, re-ran 229 tests on a frozen copy (all passed, type check and linter clean), and reported 15 findings. Its report is model output, not a human audit and not a security certification; its findings were each reproduced or marked plausible. This file says what was done about each. Everything marked **fixed** has a test in `src/lib/recruiting/__tests__/review-fixes.test.ts` (or in `robots-wildcards.test.ts`, `fuzz.test.ts`, `text-readers.test.ts`, `lane.test.ts`).

## What was found, and what was done

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | High | One business under several records (an office in each city) got a second first message after an opt-out on the first; the opt-out matched only the exact address or site; the reply reader missed 9 of 13 opt-outs | **Fixed.** Records on one website are one business for opt-outs, history and the queue. `www.`, subdomains, trailing dots, schemes and plus-addressing no longer defeat a match. The button carries the site and address. The reply reader catches the common phrasings and is read again over the whole log |
| 2 | High | Past 20,000 logged actions the newest ones were silently not read (a suppress returned success and did nothing) | **Fixed.** A full record refuses the next action with a plain message; the page warns at 90%; ids sort in write order so two actions in one millisecond fold in the order written |
| 3a | High | A 46-byte `Disallow` rule with several `*` made a company-site check take seconds to minutes on the worker, which is one process for every lane | **Fixed** in the shared `research/robots.ts`: a plain wildcard matcher with no backtracking, a cap on rule and path length, and a cap on the size of a robots.txt that is read. A test compares it with the old matcher on 20,000 random rules and paths (same answers) and checks the hostile rule is answered at once |
| 3b | High | Many `<script>` tags and a closing tag without `>` made the page reader quadratic (10 s at 400 KB) | **Fixed.** Once a closing tag is found to have no `>` after it, no later one is searched for. The fuzz test now has this shape |
| 4 | Medium | Claims written under the `--` line (a client list, "guaranteed") were never read | **Fixed.** The footer is read for stock phrases, claims and false closeness; the sender's own name, business and address are taken out first |
| 5 | Medium | A note for a contact form skipped every footer and address rule | **Fixed.** Same footer rules as email |
| 6 | Medium | Correcting a company's website kept the old mailbox | **Fixed.** The gate blocks an address that is not on the company's site as it stands; the worker drops the old mailbox and reads the new site |
| 7 | Medium | Markdown escaping let a pipe, a link, an image or an address in a company name or title break the table or become a live link | **Fixed.** Every character Markdown reads as markup is escaped; links are only ever the two web addresses the list itself prints. | 8 | Medium | A person's name and phone number could be stored as a role title; XML fields were uncapped (a 3.9 MB title made a 7.8 MB document) | **Fixed in part.** Addresses and phone numbers, and the name written next to one, are cut; every text field is capped. **Remains:** a name written alone in a public title cannot be told from a role, so the claim is "no person is sought out, listed or profiled", not "no name can ever pass through" |
| 9 | Medium | A company's "no cold emails", "no recruiters or agencies" and similar notices were missed; employers that said so were still in the list | **Fixed.** Wider set of phrasings (tested against sentences that merely contain the words); those employers are left out of the list |

The page type comes from the path only |
| 11 | Low | One damaged row in the log (a good envelope, a bad payload) made the page, the API and the worker fail | **Fixed.** Each row is checked before it is applied; a bad one is left out, counted, and shown on the page |
| 12 | Low | The follow-up clock started at UTC midnight (as little as 6 days after a late send); an old typed date made a follow-up ready at once | **Fixed.** Whole days from the end of the day typed; a date cannot be earlier than the day before approval |
| 13 | Low | Ties in time broken by a random id (an approval and an edit in one millisecond); withdrawing and re-approving the process, or changing a setting and back, revived old approvals unseen; a sent message could be rejected through the API | **Fixed** |
| 14 | Low | A subject accepted a line break; `add-board` accepted `constructor`; `?minDays=abc` dropped the 45-day floor; the request body was read before its size was checked | **Fixed** (the body is read up to the limit and no further) |
| 15 | Plausible only | In shared code used by other lanes: `safeFetch` looks up a host again after checking it; robots.txt is not re-checked on a redirect target; robots.txt fetches are outside the 110-request budget; the robots body had no cap | The cap is **fixed** (see 3a). The other three are **left as they are and documented here**, below |

## The second review: of the fixes to the first

The fixes above were reviewed in turn, by another session that had not written them (diff `edaa2ef4..867a19ec`). It found that two of the fixes had made one thing worse, and it found new problems in the code the fixes added. Each finding was reproduced here before anything was changed; the reviewer's labelled sets (303 replies, 68 sentences from company pages, 138 job titles) are kept as test fixtures in `src/lib/recruiting/__tests__/fixtures/`, together with a second set of replies and sentences written afterwards, and the tests are in `review2-fixes.test.ts` (and `robots-wildcards.test.ts`).

| # | Severity | Finding | Status |
|---|---|---|---|
| A | High | The wide net for opt-out replies filed 35 of 127 replies that WANTED the message as opt-outs (a quoted copy of our own footer, a signature with "Unsubscribe from our job alerts", "don't call me, email is fine", "Stop by Tuesday"), and missed 51 of 176 refusals. A false opt-out sets the whole business and its website aside, for good, with no way back | **Fixed.** The reader looks at the sender's own words only (quotes, forwards, our footer, signatures and newsletter footers are cut first), counts a plain request to stop however long the reply is, counts a bare "no thanks" only in a short reply that asks for nothing, and leaves alone a reply that asks a question, sends us elsewhere or limits only the phone. The shared classifier no longer files an opt-out. An opt-out read from a reply can be **undone** from the business's card ("That was not an opt-out: allow contact again"); one the owner made by hand cannot. Measured: 0 of 127 wanted replies filed, 0 of 176 refusals missed on the reviewer's set; 0 and 0 on 104 more written afterwards (first run on those: 4 mistakes, corrected with general rules, not case by case) |
| B | High | After a setting that changes how a message reads was changed, or the process was withdrawn, a message already marked as sent disappeared from the page (the list was built from approvals, which those actions clear), and with it the follow-up | **Fixed.** The text that was approved is recorded with the "sent" entry, and the page lists sent messages from that record. A "sent" entry from before the text was kept with it still shows, as long as the approval was in the log before the setting changed |
| C | High | An opt-out was kept by the record's website *as it stood when the page was drawn*, so correcting or re-reading the website let another record on the old site through; a board read dropped the record's website, city, "no solicitations" notice and address check (so a corrected website was re-applied, and the address dropped again, on every run); and a board's website replaced the domain the owner had set | **Fixed.** The opt-out records the website and address as they stood when it was given. A board read keeps everything else known about a business (website, city, notice, when its site was last read, country, states, and that a staffing business found on the map stays one) and only adds a domain when there is none |
| D | Medium | Every customer of a site builder shares a registrable domain, so two unrelated companies on `wixsite.com`, `vercel.app` or `github.io` were "one business" (an opt-out from one set aside the other), and a LinkedIn or job-board page could be kept as a company's website | **Fixed.** `site.ts`: a customer of a shared host is its own site under that name; the host itself, social and directory pages and applicant-tracking systems are nobody's own site. Applied to the map data, the board reads, the owner's website entry, the address search and the sample |
| E | Medium | Contact scrubbing left a name with an accent or a particle ("María", "Ana de la Cruz"), missed full-width digits, a run of ten digits, "1-800-FLOWERS" and "jane [at] acme [dot] com", left "1" of "1-800-…", and cut a labelled job id ("Job ID: 1234-5678-9012") | **Fixed.** Read in any script after normalising, everything from the first contact detail on is cut, with the label and the name beside it; ids, dates, zip codes, salaries and shift hours are left alone. On the reviewer's 138 titles exactly the 11 that carry a way to reach someone change |
| F | Medium | A robots.txt of 505 KB of rules, each with a dozen `*`, asked about a long path took 23.8 seconds on the one process every lane shares; and a path over 4,096 characters was "matched" by every rule, so a long `Allow` made it permitted | **Fixed** in the shared `research/robots.ts`: plain rules are compared directly, the whole answer has a budget of two million comparisons (when it runs out the answer is "no": a file too hard to read is not consent), and an over-long path is refused when the file forbids anything at all (a file with no Disallow answers as it always did) |
| G | Medium | 30 of 53 ordinary sentences were read as "we do not want to be approached" ("Our recruiters will not email you from a Gmail address", "We never sell your data to third-party vendors", "No vendor lock-in") | **Fixed.** A notice is a sentence of one of a few shapes (a short "No …" line made of nothing but the unwelcome sender; "we do not accept unsolicited …"; "we do not work with third-party agencies"; a line addressed to agencies telling them not to contact US or our people). 0 of 53 ordinary sentences, 0 of 15 notices missed; 0 and 0 on 30 more written afterwards |
| H | Low | The follow-up opened at UTC midnight, which is the evening before in Los Angeles; a form address with an "@" in its query was read as belonging to what follows the "@"; a log row with a day that does not exist (`2026-02-31`) or a time that is not one could break the clock; a signed agreement with no reference made a "client"; an invoice paid in two parts was refused as a duplicate; looking up a set-aside site compared it with every opt-out; the page did not say why no message was prepared; a company named `evil.com/login` became a link in a viewer that links bare addresses; a site in its own alphabet did not match its encoded name; a full record refused an opt-out | **All fixed** (noon UTC on the 8th day, which is 5 a.m. in Los Angeles; the host of a web address is parsed as one; bad days and times leave the row out and count it; an agreement needs a reference; one invoice has one entry for each day money arrived; the lookup costs the labels of the name; the page lists the composer's reason; dots between letters are escaped; names are compared in their encoded form; opt-outs, logged replies and a withdrawal have a reserve of 500 entries beyond the 20,000) |
| I | Plausible only | The cap on the log is checked by counting and then writing, so two requests at the same moment could pass it by one | The read window is now 600 entries beyond the cap, so a row written past it by a race is still read. **Not made atomic.** One owner clicking in turn cannot do it |

**What this review changed about how to read the numbers.** The labelled sets above were used to tune the readers, so the 0-and-0 scores on them are not an estimate of how the readers will do on real replies and real company pages. The sets written afterwards are the fairer measure: the reply reader made 4 mistakes in 104 on its first run, the notice reader 3 in 30, and both were then corrected with general rules. Expect a few mistakes on real text. They cost little by design: a missed opt-out leaves a reply on the list for the owner to read (and the follow-up is never prepared once a business has answered), and a wrongly filed one is one click to undo.

## The third review: of the live-demonstration commit

The commit that prepared the live demonstration (`377e5afe`, 34 files) was reviewed by a third session that had not written it, with the code, the tests, fresh sets of replies and company-page sentences written for the purpose, a hostile-input harness, and a check that the lane's 330 tests make no network attempt (they make none). Its verdict on the shared code (`research/robots.ts`, `cloud/work-queue.ts`, `hq-actions.ts`, `package.json`, `.gitignore`) was **safe to merge while the lane is off**, with one defect that matters once the lane is switched on (M1). Each finding was reproduced here before anything was changed. The reviewer's sets are kept as fixtures (`fixtures/notices-third-review.json`) and the tests are in `review3-fixes.test.ts`.

| # | Severity | Finding | Status |
|---|---|---|---|
| H1 | High | The reply reader froze the web process on a pasted reply of about 230 characters (a repeated group whose alternatives overlap: "any more" and "anymore"); a few more repeats took minutes to hours. The text is written by an outsider | **Fixed.** No overlapping alternatives, every repeated group capped. A test repeats every pair of the reader's words after every opener, 134,000 times, and fails if any answer takes 50 ms |
| H2 | High | The list contained roles nobody had seen for weeks (a role that left a feed was kept 45 days; a Hacker News post became "long-open" at day 45 although its thread was no longer read) | **Fixed.** A role counts as open only if a read saw it listed in the last 14 days; the list has a "Last seen listed" column and says so; the page and the files agree |
| M1 | Medium | The robots.txt cache in the shared reader was keyed by site only, so one lane's answer served another lane's bot name | **Fixed.** Keyed by site and bot name; a test for both directions |
| M2 | Medium | The notice reader missed 42% of fresh notices (10 of 24; on my own 30 fresh notices it missed 26), and employers whose site was never read were listed as if checked | **Fixed in two parts.** The reader knows more wordings and a second, wider reading passes on probable notices with their words (see 02). **Accepted, and written here so they are not forgotten:**

- **L4** history folds by the time stamp of each entry, so a clock stepped backwards could let an earlier approval beat a later withdrawal. A one-owner side business on a server clock does not do this.
- **L5** a few ways of writing a phone number or an address still pass the contact scrubber (`+49 30 901820`, `214 · 555 · 0183`, `maria at acme.com`); a name with no separator before a removed address can stay. The claim stays "no person is sought out, listed or profiled".
- **L10** a pass can take about six minutes rather than two: robots.txt fetches for an unreachable host are not counted against the budgets, and `Crawl-delay` is read and then ignored.
- **L12** the cap on the log is checked by counting and then writing, so simultaneous requests could pass it by their number. One owner cannot do it.
- **P1** (shared, existing for every cron kind) after one retry a cron job keeps its past `runAt` and is due on every worker pass; a retried `RECRUITING_TICK` would run every two minutes instead of thirty. Needs a database to show; check on the first live day.
- **P2** the address is resolved, checked and resolved again by the fetch (shared, unchanged since the first review).
- **P3** a map entry's website tag is not checked, in the worker, to belong to the business it is on. The owner sees the website and the page where the address was printed on every card, and the live demonstration checks that the site names the business.
- **P4** the worker's seed job is found by its title; editing the title would seed a second one.
- **Other languages.** A reply in German or Spanish is left to the owner. A sentence that probably is a notice from a law firm ("solicitors") is passed on although it is not one; the cost is one prospect.
- **First live read.** The review's ranking of what will fail first stands: the company-site reader returns nothing for sites that write `href='/contact'` with single quotes or hide addresses with scripts; Workable's endpoint is the old one; EU-hosted Lever accounts and SmartRecruiters accounts with more than 100 postings are not read fully; RemoteOK may challenge a data-centre address; Overpass answers 429 or 504 at busy times. None is fixed in advance because nothing live has been read.

## Limits that remain

1. **Three behaviours of code shared with other Amber lanes are unchanged:** the address check in `src/lib/api-v1/url-guard.ts` resolves a host and then the request resolves it again (a hostile DNS answer could differ between the two); the robots.txt rule of a company site is not checked again on the page a redirect leads to; and the robots.txt requests are not counted against the lane's 110-request budget. They were left alone because they belong to code that other lanes run in production, nothing could be run against a live host from the build environment, and a change there is a change to all of them. Each is small in this lane (the lane reads public pages at low rates and keeps only text), and each should be a separate, reviewed change.
2. **The review was another model's work, in the same environment.** It could not reach any live host either. It did not look at deployment, secrets handling in Railway, or the database itself.
3. **No live read has ever happened.** Nine of the twelve source adapters were written from documentation or search excerpts (see 03-lead-sources). The first read on the production worker will show which of them need a fix.
4. **GitHub Actions cannot start jobs on this account (billing),** so none of this has been through the project's CI. The local runs are: 367 recruiting tests in 25 files, 37 in the shared web-hazard ratchet (one of which flagged a comment in the recruiting reader, now reworded), the other tests that use the shared robots.txt code (all pass except five in `route-to-organization.test.ts`, which need a database that this environment does not have), the type check and the linter.
5. **The decision log has a hard end at 20,000 entries.** At the pace of a one-person side business that is years away; the page says so well before it, and an archive step would be a small separate change.
6. **Legal points** are unchanged and still need a lawyer (02-voice-and-compliance, last section).

## What the review found sound

The owner-or-admin check and the same-site check on the API; request size handling; that the server, not the browser, supplies the text of an approved message; that `__proto__` and `constructor` in JSON pollute nothing; that regions needing consent, placement and split fees cannot be switched on; that suppress, reply, edit and withdrawing the process each beat an earlier approval; that an unapproved process, personal addresses, a missing email footer and the default region all hold; a 49-address battery for role mailboxes; that the ledger needs proof plus confirmation; that every fetch goes through the guarded fetch; that there is no sending code and no unescaped HTML; that no XML entity expansion occurs; that the wording check and the reply classifier are linear at 600 KB; and that the worker and the page write separate rows.
