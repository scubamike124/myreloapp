## What "ready" means here, and what it does not

Ready means all of these held when the pilot runner (`scripts/offers-run.ts`) was run on clearly invented buyer files: the planted problems were found with no false finding; the quality checks passed (and a report with a failed check says "Not ready to send"); the file the buyer receives is a folder a non-technical person can open (a web page, one CSV per table, a README) and matches what the page promises; everything the page asks the buyer to send can be read by the runner; no way was found to a wrong report that passes every check (a PDF, a photo, a bot-check page, reversed signs and an unreadable row now stop or show in the report); and a person reviews it before it is sent.

It does **not** mean a buyer wants it, that anyone has paid, or that the work needs no person. Around the runner every pilot is manual today: the owner reads the inquiry and replies, agrees scope, price and date in writing, sends one payment request by hand, receives the files by email, someone with this repository runs one command, reads the reviewer's notes and the report, sends the folder (zipped) by email, records the result on #105, and deletes the files after 60 days or when asked. Nothing in that path is automated, and the owner confirms each step. The first run of any of it with a real buyer's real files has not happened.

## How it was proved, and how far to trust it

1. **The audit.** An agent ran 151 recorded runs of the pilot runner on invented inputs it built with a countable set of planted problems (a messy variant, a negative set, a gate test and a client-mode run per offer) and checked each report against what was planted by scripts that read the ground truth, not the product's output. Its working proof is `evidence/fulfilment/FULFILLMENT-PROOF.md`; its 12 commits fixed what it found (amberai #799).
2. **My independent check.** I did not rely on the agent's account. From a clean checkout of its last commit I re-ran the ten main commands as recorded (all exit 0, 1.6 to 1.8 seconds each) and ran its planted-problem checkers on my outputs: offers 1, 2, 3, 5, 6, 7 and 9 pass every check (20, 14, 26, 15, 9, 10 and 35); offers 4, 8 and 10 report exactly the gaps listed above. I rendered the ten web pages in Chromium (no outside requests from any of them), read offers 1 and 3 on screen and offer 7's folder and CSV files as text, and reviewed the safety-relevant code change (the wording scans no longer count a word that is only in the client's own files), found one hole in it (a cell that was only "Certified" excused the word everywhere) and fixed it with a test before the merge. The commands, the invented inputs and the resulting delivery folders are in `evidence/fulfilment/<offer>/`.
3. **Limits.** Everything ran on invented data. Real exports vary more than any fixture, so the first real file for each offer may fail to import; the pages already say a full refund applies if no report can be produced from readable files. The importers' line numbers count non-blank rows, so after a blank line a "Line 37" note can be one row off in Excel (the notes also name the invoice or message). Nothing was opened in Excel or Numbers (no spreadsheet application here); the CSV files were checked with a parser (one row width, byte-order mark, CRLF). Time to produce is measured only for the runner (23 to 445 ms of processing); the human steps were not timed, because no real buyer exists yet, so no fulfilment time is claimed.

## The terms shown on a ready page (a proposal for the owner to confirm)

Modelled on the live Website Snapshot's own terms and written in `src/lib/offers/terms.ts`. **Payment:** once, before work starts, after scope, price and date are agreed in writing; one payment request by email; nothing is charged on the page. **Turnaround:** a target in business days, never a date, and the date is confirmed in writing before payment. **Refunds:** a full refund if no report can be produced from the files sent and others readable cannot be sent; none once a report has been delivered, because the work has been done (for a pilot with several deliveries, the deliveries not yet made are refunded). **Delivery:** by email, reviewed by a person: a web page and CSV files. **Data:** used only for the report, kept up to 60 days, deleted sooner on request, never sold. **Your side:** the buyer confirms the files are theirs to share. Nothing claims a result, a saving or a certification. The owner should confirm or change the turnaround targets, the refund rule and the retention before the first buyer relies on them.

## Counting rules for the promotion test

Only the seven ready offers are promoted, one post per offer, one weekday at a time (the order is in `ads/PROMOTION-PLAN.md`), through a connected Facebook Page; an offer with no `ready` record is never posted and its page says it is not taking orders. An inquiry is never revenue; revenue is counted only from a verified payment or an owner `offer-record: ... paid` line with its reference, and refunds net against it. Self-tests and invented data are excluded.
